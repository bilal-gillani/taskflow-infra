# TaskFlow — Production Infrastructure & CI/CD Pipeline

This repository contains the infrastructure-as-code (IaC) and configuration management for **TaskFlow**, a two-tier PHP web application. It demonstrates a complete, production-grade DevOps workflow on Microsoft Azure.

## 🛠️ Technology Stack
- **Terraform** — Infrastructure provisioning (Azure VMs, VNet, Subnets, NSGs, Key Vault).
- **Ansible** — Configuration management (Apache, PHP, MySQL, App Deployment).
- **GitHub Actions** — CI/CD automation for both infrastructure changes and application deployments.
- **Azure AD (OIDC)** — Secret-less, federated identity for GitHub Actions.

## 🏛️ Architecture

```text
┌──────────────────────────────────────────────────────────────┐
│  GitHub                                                      │
│                                                              │
│  [App Repo: taskflow-app-source]                             │
│    push to main ──► deploy-app.yml ──► SSH → git pull        │
│                                                              │
│  [Infra Repo: this repo]                                     │
│    PR to main   ──► infra-cicd.yml ──► terraform plan        │
│    merge to main──► infra-cicd.yml ──► terraform apply       │
│                                        ──► ansible site.yml  │
└──────────────────────────────────────────────────────────────┘
               │ SSH                           │ SSH (ProxyCommand)
               ▼                               ▼
    ┌────────────────────┐         ┌────────────────────────┐
    │   App VM           │         │   DB VM (private)      │
    │   Ubuntu 24.04     │◄───────►│   Ubuntu 24.04         │
    │   Apache + PHP 8.3 │  MySQL  │   MySQL Server 8.0     │
    │   /var/www/html/   │  3306   │   taskflow DB          │
    └────────────────────┘         └────────────────────────┘
            │ Public IP                    │ Private IP only
            │                              │ (reached via App VM as jump host)
    Azure VNet (10.2.0.0/16)
    App Subnet: 10.2.1.0/24      DB Subnet: 10.2.2.0/24
```

### Security Highlights
- **Private Database:** The DB VM has no public IP. Ansible configures it securely over a ProxyCommand SSH tunnel routed through the App VM.
- **Network Security Groups (NSGs):** Replaces software firewalls like `fail2ban` or `ufw` to centrally manage inbound rules at the Azure VNet level. Only the App subnet can reach the DB subnet on port 3306.
- **Dynamic Secrets:** The MySQL database password is auto-generated by Terraform, stored securely in Azure Key Vault, and fetched dynamically by Ansible directly into the environment variables (`MYSQL_PWD`), keeping it out of logs and bash history.
- **Secret-less CI/CD:** Uses Azure OpenID Connect (OIDC) to authenticate GitHub Actions to Azure without storing long-lived credentials.

## 🚀 CI/CD Pipelines

### 1. Infrastructure Workflow (`infra-cicd.yml`)
When changes are made to `terraform/` or `ansible/`:
- **On Pull Request:** Runs `terraform fmt`, `init`, `validate`, and `plan`. The plan is posted as a PR comment for review.
- **On Push to Main:**
  1. Authenticates to Azure via OIDC.
  2. Runs `terraform apply` to provision/update Azure resources.
  3. Writes the `terraform.tfvars` and SSH keys securely from GitHub Secrets.
  4. Dynamically builds the Ansible inventory using Terraform outputs.
  5. Waits for VM SSH ports to become responsive.
  6. Runs the Ansible playbook to configure the VMs.

### 2. Application Workflow (`deploy-app.yml`)
*Note: This workflow lives in the application repository.*
- **On Push to Main:**
  1. Runs robust PHP syntax linting.
  2. Connects to the App VM via SSH.
  3. Temporarily marks the directory as safe for git and pulls the latest code.
  4. Restarts Apache.
  5. Performs a cURL health check (following redirects) to verify the app is returning an HTTP 200 OK.

## ⚙️ Setup Instructions

To deploy this architecture yourself, you must configure the following in your GitHub Repository Secrets:

### Infrastructure Repo Secrets
| Secret Name | Description |
|---|---|
| `AZURE_CLIENT_ID` | OIDC Service Principal Client ID |
| `AZURE_TENANT_ID` | Azure Tenant ID |
| `AZURE_SUBSCRIPTION_ID` | Azure Subscription ID |
| `TF_VARS_FILE` | The full contents of your `terraform.tfvars` file. *(Note: In a true GitOps flow, non-sensitive vars should be committed to Git, while sensitive ones use `TF_VAR_` secrets).* |
| `ANSIBLE_SSH_PRIVATE_KEY` | Your private SSH key used to connect to the Azure VMs. |

### Application Repo Secrets
| Secret Name | Description |
|---|---|
| `APP_VM_IP` | The public IP of the App VM (from `terraform output`). |
| `ADMIN_USERNAME` | The SSH username for the VM. |
| `DEPLOY_SSH_KEY` | Private SSH key matching the deploy public key configured by Ansible. |

## 🧠 Lessons Learned & Best Practices
- **Ansible ProxyJump:** When routing Ansible through a jump host, appending `-i` flags to a `ProxyJump` argument causes silent authentication failures. Using a strict `ProxyCommand` with explicit IdentityFiles and KeepAlives is significantly more robust.
- **Git Dubious Ownership:** Running `git pull` as `root` in a directory owned by `www-data` triggers Git's security protections. Always configure `git config --global --add safe.directory` during deployment.
- **Database Passwords:** Passing passwords containing special characters (like `!`, `$`) directly into shell commands (`mysql -p{{ password }}`) causes bash syntax errors. Always pass secrets via the environment (e.g., `MYSQL_PWD`).
- **Secret Management:** Storing full config files like `terraform.tfvars` as GitHub Secrets bypasses GitOps workflows. Separate your configuration (committed to Git) from your secrets (injected via `TF_VAR_`).
